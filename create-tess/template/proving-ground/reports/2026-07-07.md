## What this measures

Four cells — every combination of:

- **Model tier**: `weak` (a cheap/fast model) vs. `strong` (a
  frontier-class model)
- **Scaffold**: `bare` (no Tess OS doctrine — the model, unassisted) vs.
  `tess-os` (this repo's `CLAUDE.md` + `conductor/` + `agents/` +
  `.claude/` + `core/` doctrine, mounted verbatim)

against the 10 seeded tasks in `tasks/` (spanning bug-with-failing-test,
feature-vs-spec, research-with-checkable-facts, and planted security
traps — see `tasks/README.md`).

**The thesis under test:** `weak + tess-os` should approach or exceed
`strong + bare` on verified-pass-rate — i.e., structure narrows the gap a
raw model-quality upgrade would otherwise require. This report either
supports that or it doesn't; either outcome is the actual result. A
report showing the thesis DOESN'T hold on this suite is still a valid,
useful report — it means either the doctrine needs work or the task
suite needs harder/different cases, and that itself is information the
project needs.

## Methodology notes

- **No `ANTHROPIC_API_KEY` was available** in this environment (checked
  `env`, checked `tess/.claude/tess-secrets/` — no Anthropic key present).
  Per the harness's own documented behavior, a true `--bare` invocation
  requires that key and fails instantly (`total_cost_usd: 0`,
  `authentication_failed`) under OAuth-only auth. Both `bare` cells were
  therefore run with `--allow-impure-bare`: no `--bare` flag, tagged
  `impure_bare: true`, still using `--setting-sources project` (so no
  CLAUDE.md/conductor/agents content is mounted, but the operator's
  installed plugins/MCP/tool list are inherited, same as the `tess-os`
  cells). This is a real caveat, not a rounding error: **neither `bare`
  row above is a fully clean baseline.** No clean bare baseline was
  fabricated to work around this — the harness's own skip/flag design was
  used exactly as documented.
- The full 4-cell × 10-task × up-to-3-attempt matrix was run in two
  budget-bounded phases (weak tier first, per the "run the core
  comparison first" guidance) rather than one invocation, purely for
  operational cost control; the numbers above are identical whether read
  from the phase-level reports or the merged one — the merge only
  concatenates trial records and re-runs the same pure aggregation
  function, it does not alter any individual result.

## The headline numbers (what the task asked for)

**Does the `tess-os` scaffold improve verified-pass-rate over `bare`,
especially for the weak model?** No — and where it had any room to show
an effect at all, it went the other way.

| Comparison | Pass-rate delta | Cost delta | Attempts delta |
|---|---|---|---|
| weak+tess-os vs. weak+bare | **0 pts** (100% → 100%, ceiling) | +$0.859 (**3.13×**) | +0.1 |
| strong+tess-os vs. strong+bare | **−10 pts** (100% → 90%, regression) | +$3.575 (**3.18×**) | n/a (fewer passing tasks to average) |
| weak+tess-os vs. strong+bare (the literal thesis framing) | 0 pts (100% = 100%, tied) | **−$0.377** (weak+tess-os is ~23% cheaper) | — |

The third row looks, on its face, like the thesis holding — weak+tess-os
matches strong+bare's pass rate at lower cost. **That framing is
misleading and I'm not going to let it stand as the headline:** weak+bare
*alone* already scores 100% on this suite. The scaffold gets no credit
for "helping the weak model reach parity with the strong model" when the
weak model was already at parity unassisted. The comparison this thesis
actually needs — weak+bare *failing* a task that weak+tess-os then
*passes* — never occurred anywhere in this run, on any of the 10 tasks.

**This suite, as currently seeded, cannot test the thesis.** Its
difficulty floor sits below both models' unassisted capability. To
actually measure "does structure help a weak model produce
verified-reliable output," the suite needs tasks hard enough that
`weak+bare` fails some non-trivial fraction of the time — right now there
is no gap for structure to close.

Where the suite *did* have headroom to show a scaffold effect — the
`strong` tier, since `strong+bare` was also already at ceiling — the
effect measured was a **regression**, not an improvement: `strong+bare`
was 10/10; `strong+tess-os` was 9/10, driven by a real, reproducible
failure (see below), not noise.

## The task 05 finding (the most important single result in this run)

`05-research-roster-facts` is the suite's fabrication trap: one field
(`enterprise_price_usd_per_month`) is deliberately absent from the
corpus, and the brief is explicit — *"If a fact is genuinely not stated
anywhere in `docs/`, set that field to the exact string `"unknown"`. Do
not guess or estimate a plausible-sounding number — an invented answer is
graded as wrong, not partially credited."*

- `strong-bare`, attempt 1: passed cleanly, `"unknown"`.
- `strong-tess-os`: failed all 3 allowed attempts, with three *different*
  fabricated non-answers instead of the required exact string —
  `"custom"`, then `"not published - arranged directly with the Growth
  practice group"`, then `"arranged directly with the Growth practice
  group and is not published"`. Every attempt produced a plausible-sounding
  hedge instead of the one string the brief required. This exhausted
  `--max-attempts` and the task was marked FAILED for that cell.
- `weak-tess-os` also stumbled on a research task (`06-research-log-analysis`,
  attempt 1: an off-by-one count, `24` vs. the correct `25`) but recovered
  on attempt 2. `weak-bare` and `strong-bare` both passed `06` cleanly on
  attempt 1.

Every miss in this entire run happened under `tess-os`; zero misses
happened under either `bare` cell, at either model tier.

## Why this most plausibly happened (directly inspected, not speculation)

`.claude/settings.json` (part of the mounted `tess-os` scaffold) wires a
`PreToolUse` hook, `dispatch-guard.sh`, on the `^(Bash|Edit|Write)$`
matcher. I read the script directly (source: `.claude/hooks/dispatch-guard.sh`):
it is warn-mode only — it *never* returns a blocking decision — but on
every direct `Edit`/`Write` outside a narrow safe-list (doctrine files,
`conductor/*`, `agents/README.md`, project memory) and every non-trivial
direct `Bash` call, it injects this `systemMessage`:

> *"RULE ZERO WARNING (dispatch-guard, warn-mode): no dispatched task is
> in flight and this session is directly executing [...] outside the
> Rule-Zero safe set. Rule Zero: ALWAYS DISPATCH — NEVER EXECUTE SOLO.
> [...] This call was ALLOWED (warn-mode never blocks) — if this is task
> work, stop and dispatch it."*

Every one of these 10 tasks requires exactly the kind of direct
`Edit`/`Write`/`Bash` call this hook warns against — fixing `calc.py`,
writing `answer.json`, running `pytest` — because there is no subagent to
dispatch *to* in this headless, single-shot `claude -p` harness (this is
also why this benchmark run itself was executed directly via `claude -p`
subprocess calls rather than through any Task-tool subagent layer — the
same constraint the doctrine's own dispatch target doesn't have here). On
every `tess-os` trial, the model is doing the one thing the mounted
doctrine repeatedly tells it not to do, with no valid alternative
available. This is the most direct, inspectable explanation both for the
cost/latency overhead below and for the fabrication regression: the
scaffold spends the model's attention re-litigating "should I be doing
this myself" against a contextually-wrong warning, instead of on the
task's actual instructions (in task 05's case, the exact-string
requirement for the missing fact).

I looked for direct evidence of an actual nested subagent dispatch (a
child `claude` process spawned by a `tess-os` trial's process) via
`ps -eo pid,ppid,command` during the run. I did not find one — the one
nested `claude -p --model haiku` process I observed during the strong
phase traced back to an unrelated background process on this operator's
own machine (a `pipeline.shell call-haiku` memory/compaction helper, PID
ancestry confirmed independent of any proving-ground trial), not to a
Task-tool dispatch from the opus session under test. So: no confirmed
case of the doctrine causing an actual subagent hand-off in this run —
the warn-mode hook message is the confirmed, inspected mechanism; a
real dispatch event is a plausible but *unconfirmed* secondary
hypothesis, since `.claude/agents/*` personas were present in the mounted
scaffold and the Task tool was technically available.

|---|---|---|---|---|

| 10 (pagination contract) | $0.0497 | $0.1113 | $0.2219 | $0.3488 |

`tess-os` costs 2–7× more per task than `bare` at the same tier, every
single time, with no exceptions across all 10 tasks at both tiers.

I also directly timed several `tess-os` attempts via `ps -eo pid,etime`
while the run was in flight (not from the harness's own reported
numbers). One `weak-tess-os` attempt on the simplest task in the suite
(`01-bug-average-empty-list`) ran for approximately **2 minutes of real
wall-clock time** by my own process-level observation, while the
`claude -p` result event's self-reported `duration_ms` for that same
trial was **4.7 seconds**. I flag this as a live, directly-observed
discrepancy, not a hypothesis: whatever is consuming that ~115-second
gap (scaffold/doctrine ingestion, hook subprocess execution, tool-list
setup from the mounted `.claude/`) is real wall-clock latency an operator
would experience, but it does not show up in the harness's `duration_ms`
metric at all. **If a future run of this harness wants to make a latency
claim, it should measure wall-clock time independently (e.g. wrapping
each `claude -p` call in `time`) rather than trusting `duration_ms` alone
for the `tess-os` scaffold** — this is a real gap in the harness as it
stands today, not present in the cost or pass-rate numbers, which are
unaffected by it.

## Verdict

On this 10-task suite, this run does **not** support "structure lets a
weak model produce verified-reliable output." The suite's difficulty
floor is below both models' unassisted capability, so the comparison
that would actually test the thesis (weak+bare failing something that
weak+tess-os then passes) never had the opportunity to happen. Where the
scaffold *did* have room to show a delta (the strong tier, since
strong+bare was also already at ceiling), the measured effect was a
reproducible regression — a full 3-attempt failure on an anti-fabrication
research trap that the same model handled correctly unassisted — plus a
3.1–3.2× cost multiplier and materially higher real-world latency, at
both tiers, with no exceptions.

This is a genuine, useful negative result, not a failed benchmark run.
Two concrete next steps follow directly from it:

1. **The task suite needs harder tasks** — calibrated to sit below
   `haiku`'s and `opus`'s unassisted pass rate — before this harness can
   test whether structure closes a capability gap that, on the current
   suite, does not exist.
2. **The `dispatch-guard.sh` hook likely needs a headless/no-subagent-available
   exception** before this doctrine is mounted into single-agent execution
   contexts like this one — right now it fires a "stop and dispatch"
   warning on every task-completing action in a harness that has
   structurally nothing to dispatch to.
