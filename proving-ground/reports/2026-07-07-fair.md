## Why this run exists

The first run (`2026-07-07.md`) concluded the 10-task suite (`01-10`)
couldn't test the thesis at all — both `bare` cells were already at 100%,
so there was no capability gap for `tess-os` structure to close. Where the
suite *did* have room to show an effect (the `strong` tier), the measured
effect was a regression: `strong-tess-os` scored 9/10, driven by a
reproducible fabrication failure on task `05-research-roster-facts`,
plausibly caused by the `dispatch-guard.sh` hook's "RULE ZERO — stop and
dispatch" warning firing on every direct `Bash`/`Edit`/`Write` call in a
harness that has nothing to dispatch to.

Two fixes were authorized before this re-run:

1. **9 new discriminating tasks (`11-19`)**, built so the plausible first
   thing a *bare* model writes is wrong (PR #40, commit `5bded75`) — this
   is what actually gives `tess-os` a capability gap to close, if the
   thesis is true.
2. **The dispatch-guard headless fix** (PR #48, branch
   `goal-dispatch-guard-headless`, commit `b67157b`) — `dispatch-guard.sh`
   now no-ops when the caller sets `TESS_HEADLESS=1` / `TESS_NO_SUBAGENTS=1`,
   removing the friction the first run's own root-cause analysis pointed at.

### An additional, un-asked-for fix this run required (disclosed, not buried)

While verifying fix 2 with one cheap real `claude -p` call before
committing to the full matrix, I found something neither prior report nor
the harness's own docs anticipated: **this operator's environment has real
Agent/Task-tool dispatch infrastructure**, and the `tess-os` scaffold's
mounted `CLAUDE.md` (which is literally the "you are Tess, always
dispatch" persona, not a passive style guide) caused the model under test
to actually invoke it. A verification probe (`weak` model, `tess-os`
scaffold, prompted only to run `python3 --version`) produced a real
`Agent` tool call, which genuinely spawned, ran, and completed a nested
background subagent — a real JSONL transcript file was written to disk at
a path under this benchmark's own scratch directory, confirmed after the
fact. This directly contradicts the harness's README assumption ("this
headless, single-shot `claude -p` harness" has "no subagent to dispatch
to") and the first report's conclusion ("no confirmed case of the doctrine
causing an actual subagent hand-off in this run") — that conclusion does
not hold in this environment.

This is a real cost/safety issue, not just a measurement wrinkle: an
uncontrolled nested dispatch on a benchmark task ("fix this rounding bug")
could, in principle, resolve to a child session with access to whatever
MCP servers/credentials that session's own settings resolve, completely
outside this trial's cost/timeout accounting. I closed it before running
the real matrix by adding `--disallowedTools Agent,Task` to **every**
`claude -p` invocation this harness makes (both `bare` and `tess-os`, so
the safety net is symmetric and neither arm is advantaged by it). Verified
directly: with the flag set, the same probe's `Agent` tool call is
rejected (`"No such tool available: Agent... not enabled in this
context"`) and the model falls back to executing directly — the behavior
the harness's cost/pass-rate model already assumed. Re-ran with a live
harness call (`run.py` itself, not a manual probe) on a `trap` task after
the fix and confirmed no `.output` transcript files or lingering `claude`
processes were left behind.

Separately, I confirmed the `dispatch-guard.sh` hook **does** actually
execute during real headless `claude -p` calls (a marker-file side effect
fired), but its `systemMessage` never appears anywhere in the
`--output-format json` event stream, under either `TESS_HEADLESS` setting.
Whether/how that message reaches the model's context in headless mode is
unconfirmed either way — noted here as an open question for the harness,
not something this run's methodology depends on: the fix is applied at
its source (the hook itself correctly no-ops), independent of whether its
effect is directly visible in the JSON transcript.

## The task 12 finding (the most important single result in this run)

`12-bug-csv-quoted-fields` is the suite's "confident-wrong" CSV trap: the
obvious `line.split(',')` implementation passes on plain rows and silently
mis-parses any row with a quoted comma or an escaped quote; the correct
fix is to actually use `csv.reader`/equivalent quote-aware parsing.

- `weak-bare`: passed on attempt 1, cost $0.0591.
- `weak-tess-os`: failed on **all 3** attempts, cost $0.0588 + $0.0466 +
  $0.0579 = $0.1633 total, identical grade reason (`"5 CSV row(s) parsed
  wrong"`) every time — the model made three attempts and never actually
  landed on quote-aware parsing.
- `strong-bare` and `strong-tess-os` both passed on attempt 1.

The same weak model, given the identical task, solved it unassisted and
failed it three times when loaded with the full `tess-os` doctrine
(`CLAUDE.md` + `conductor/` + `agents/` + `.claude/` + `core/` — a large
amount of context that has nothing to do with CSV parsing). The most
direct, available explanation is context/attention dilution: a small model
has a limited effective budget for "notice the actual technical edge
case," and a large irrelevant doctrine payload competes for that budget.
This is not proven by this run (no attention-tracing was done — this is
the same category of inference the first report's dispatch-guard
explanation was, clearly labeled as such), but it is the most plausible
account consistent with what was directly observed: three attempts, three
identical failures, at 2–3× the cost of the one attempt that worked.

## Verdict

**On tasks 11–19, this run does not support "structure lets a weak model
produce verified-reliable output."** With a task suite actually calibrated
to give `tess-os` a capability gap to close (unlike the first run's
suite), the weak model performed *worse* with the scaffold than without
it — lower pass rate, more attempts, 2.7× the cost — driven by a real,
reproducible failure on the CSV-quoting trap that the same model solved
unassisted on the first try.

**The dispatch-guard headless fix did remove the strong-tier regression**
observed in the first run: both `strong` cells hit 100% this time, with no
repeat of the task-05-style fabrication failure. That part of the thesis —
"the friction was the hook, and removing it helps" — is supported by this
run, at least for the strong tier. It did not, however, turn `tess-os`
into a net positive for either tier: cost overhead (1.7–2.7×) persists at
both tiers with no exceptions across 9 tasks, and the weak tier now shows
an outright pass-rate regression this run was specifically designed to be
able to detect.

**A significant unplanned finding**: this operator's environment has real
Agent/Task-tool dispatch infrastructure reachable from a headless
`claude -p` call with the `tess-os` scaffold mounted — the harness's own
"no subagent to dispatch to in this headless harness" assumption is false
in this environment, and was closed here with `--disallowedTools
Agent,Task` on every invocation (both scaffolds, for symmetry). Any future
run of this harness on a similar operator setup needs this flag (or an
equivalent lockdown) to avoid uncontrolled nested dispatch — this should
be upstreamed into `claude_driver.py` permanently, not treated as a
one-off patch for this run.

Two concrete next steps follow:

1. **The weak-tier regression on task 12 deserves direct follow-up** —
   compare the actual transcripts (not just grade reasons) for
   `weak-tess-os` attempts on `12` against `weak-bare`'s single passing
   attempt, to test the context-dilution hypothesis directly rather than
   infer it.
2. **`--disallowedTools Agent,Task` (or equivalent) should be a permanent,
   committed part of `claude_driver.py`**, not something re-discovered by
   the next person who runs this harness on a machine with live
   subagent-dispatch infrastructure.
