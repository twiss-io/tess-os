## Threat model
The adversary is a prompt-injected or misaligned agent session, or a malicious contributor, with write access to the working tree. It wants to (a) land bytes in a protected or security-tier file, or outside the repo, through a render or publish path; (b) get code run through a rendered runtime artifact (a Gemini `!{...}` shell block, an `@{...}` file inline, or an implicitly invoked skill); or (c) weaken the gate, verdict, policy or key trust anchors.

## Attack surface added by this PR
- The new `gemini` render target. It writes `AGENTS.md`, `GEMINI.md` (a header plus `@./AGENTS.md`) and `.gemini/commands/tess/<name>.toml`. It does not write `.gemini/settings.json`, `.gemini/policies/**` or any hook.
- The `codex` target now writes `.agents/skills/tess-*/**`, and the new owned glob `.agents/skills/tess-*/**` beats the `.agents/**` never_touch.
- eng-b's `render_outputs` records and multi-entry status handling. All render writes still go through `guarded_write`.
- `create-tess` now leaves `reviews/verdicts/**` out of scaffolds.

## What I checked
- **Write containment.** Symlinked `.gemini`, `.gemini/commands/tess`, `.agents/skills` and `.agents/skills/tess-wake`, pointing at outside and in-root directories, never received a write. Gemini skips them and the codex target fails closed with WRITE REFUSED. `GEMINI.md`, `AGENTS.md` and `wake.toml` symlinked to `conductor/guardrails.md` were skipped, and the guardrails file was unchanged. A dangling link to an outside path was not created. A 0.1.4-shaped manifest writes nothing Gemini-shaped.
- **Injection.** Gemini command prompts go through `$ARGUMENTS` to `{{args}}` first and then trigger breaking, so `!$ARGUMENTS}` cannot rebuild `!{`. A hostile body with `!{`, `@{`, `!!{`, `@!{`, `'''`, `"""`, a trailing quote and control characters produced valid TOML, and the prompt carried no trigger. Codex skills are explicit-only (`allow_implicit_invocation: false`). Gemini also loads them from `.agents/skills` as model-activated skills behind its own consent prompt, and `adapters/gemini/README.md` says so.
- **Trust anchors.** Policy, verifier keys, workflows, contracts, security-tier doctrine and the gate, verdict and signing code have no diff. `tess.lock` changes no tier or status. The adapter manifest claims C2 / Advisory with no enforcement or parity claim.
- **Tests.** The Gemini tests fail behaviourally on 5c2d698 (26 of 27; the one pass is the test's own scanner self-test). They cover hostile bodies, a symlinked commands directory, not-owned skips and hand-edit survival.

## Residual risk
- Render outputs are normal tier, and render now keeps hand edits to them (finding 1). Detection is intact.
- The template engine copy is not gate-protected (finding 3, deferred to v0.2.1).
- The parent-symlink checks are check-then-write (TOCTOU). Exploiting that needs a local writer racing tessctl, and such a writer can change the tree directly.
- No Tess hook runs under Gemini CLI. The ship-gate is enforced only at pre-push and in CI.
- The P0 type-swap gate bypass (#71 lineage) is still open in v0.2.0.
- This approval is signed with an agent-held verifier key. Custody hardening is the first v0.2.1 item.
