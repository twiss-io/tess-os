## A13 — evaluate-then-swap (TOCTOU family)

Two sub-probes. The literal TOCTOU (content-swap) is **BLOCKED**; a related
type-swap is a **BYPASS**.

### A13a — content-swap (blob → blob): BLOCKED

The gate returns green for commit X (compliant prod change + valid signed
verdict); a malicious commit Y (no verdict) then replaces X at the same ref
(force-push / rebase / post-approval amend). `tessctl gate` is stateless — it
re-classifies whatever `base..head` it is handed — so re-running the gate on Y
independently **BLOCKS** it:

```
content_swap: blocked=True, x_green=True
  reason: "src/prod/app.py: no covering APPROVE verdict found (policy rule(s):
           prod-src; classification: prod_touching) — Decision #6 ..."
```

The engine does NOT trust its earlier green for X. The only residual TOCTOU
window — a CI/branch-protection layer that reuses X's *status check* for a
merged Y without re-running on Y (e.g. GitHub's "require branches to be up to
date" being off, so a stale green satisfies the required check) — is the
repo-admin / branch-protection boundary `README.md` already discloses, not an
engine gap.

### A13b — TYPE-swap (blob → symlink): BYPASS FOUND

**What is exploitable.** `_gate_diff_paths` computes changed paths with
`git diff --name-only --diff-filter=ACMR` (Added/Copied/Modified/Renamed). A
change that converts an existing governed **regular file** into a **symlink**
is a git *type change* — status letter `T` — which that filter **excludes**.
Independently, `_gate_git_ls_tree` drops mode-`120000` (symlink) entries
(LOW-1). So a governed path can transition from *"regular file, requires a
covering verdict"* to *"symlink, invisible to the gate"* with **no verdict
required for the transition** — it appears in neither the classifier's
changed-path set nor the tree index. The file's resolved runtime behavior is
swapped (the symlink now resolves to attacker-chosen, ungoverned content) and
the gate returns green.

Empirical result (pristine shipped engine):

```
type_swap: blocked=False
  changed_paths: ["payload.py"]        # src/prod/app.py is ABSENT
  app_py_classified: False
  reasons: []                          # nothing flagged — GREEN
```

`src/prod/app.py` (governed by the `prod-src` rule, `src/prod/**`) was
converted to a symlink pointing at the ungoverned `payload.py`; the gate never
saw `src/prod/app.py` as changed at all.

**Blast radius.** Any governed path — `src/prod/**`, `.tess/bin/tessctl`
(the engine), `core/policy/policy.yaml`, `.github/workflows/**` — can be
replaced by a symlink to unreviewed content, shipping green with zero covering
verdict, in any repo whose deploy/runtime follows the checked-out tree's
symlinks. This defeats the gate's core claim ("no prod-code change ships
without review") for the entire governed surface. (It does not, by itself,
subvert the CI *trusted-base-ref engine* extraction for A11, which reads the
engine from the base ref via `git show` — but it does mean the pushed tree's
engine and any governed prod file can be silently swapped.)

**Minimal standalone repro** (no arena, no keys — pure git + the shipped
engine; run from a checkout of this repo):

```bash
set -e
TMP=$(mktemp -d); cd "$TMP"
git init -q -b main && git config user.email a@a && git config user.name a
mkdir -p .tess/bin core/policy src/prod core/contracts
cp /path/to/tess-os/.tess/bin/tessctl .tess/bin/tessctl
cp -r /path/to/tess-os/core/contracts/. core/contracts/
cat > core/policy/policy.yaml <<'YAML'
policy:
  version: 1
  rules:
    - id: prod-src
      description: prod code
      globs: ["src/prod/**"]
      classification: [prod_touching]
      require_verdict: true
      allowed_verifiers: [Quinn]
  verifier_keys: {}
  signoff_keys: {}
  hard_floor_rules: []
YAML
echo "print('v1')" > src/prod/app.py
git add -A && git commit -qm base && BASE=$(git rev-parse HEAD)
# ATTACK: convert the governed prod file into a symlink -> ungoverned payload
echo "print('unreviewed attacker code')" > payload.py
rm src/prod/app.py && ln -s ../../payload.py src/prod/app.py
git add -A && git commit -qm 'relink app.py'
HEAD=$(git rev-parse HEAD)
TESS_ROOT="$TMP" python3 .tess/bin/tessctl gate ci --base "$BASE" --head "$HEAD" --json
# EXPECTED (pre-fix): "blocked": false, changed_paths lists only payload.py —
# src/prod/app.py's type-swap is invisible. GREEN.
```

**Fix (implemented — separate commit *after* this finding).** Add the `T`
(type-change) status to the gate's diff filter in `_gate_diff_paths` and
`_gate_changed_paths_staged` (`--diff-filter=ACMR` -> `--diff-filter=ACMRT`).
A blob->symlink change then appears in `changed_paths`, is classified under its
matching rule, and — because `_gate_git_ls_tree` still (correctly) excludes the
symlink from the tree index — has no current blob to bind a covering verdict
to, so it fails closed with a normal "no covering APPROVE verdict" block. This
is strictly additive (it only ever adds paths to classification — more
fail-closed — never removes any), so it cannot weaken A1–A12. Verified: with
the fix, A13 -> BLOCKED and A1–A12 remain 12/12 BLOCKED (before/after raw output
in the fix commit). The related `D` (deletion) exclusion is a lower-severity
quirk left documented but not closed here: a correct deletion-aware fix needs
covering logic beyond a one-character filter change (a deleted path has no
current blob to bind a verdict to), and deleting a governed file does not, by
itself, ship malicious *behavior*.

## A14 — multi-commit split-payload across separately-merged pushes

**Verdict: SLIPPED (conditional gap) — NOT a key-free bypass.**

**What is (and isn't) exploitable.** A3 proves the gate blocks a
weaken-the-policy-AND-exploit-it tamper when both halves ride the *same* push
(`base..head` unions the pre-push baseline policy — `_gate_load_policy_at_base`
+ `_gate_union_baseline_matches`). This probe tests whether that protection
composes across the push boundary by splitting the tamper into two
independently-gated merges:

- **push 1** — weaken the policy (remove the `prod-src` rule) WITH a valid,
  signed Reid verdict for the policy edit. The policy file is itself governed,
  so this half is correctly gated; it **cannot land key-free**. Result:
  `push1_blocked=False` (it lands, because a real Reid verdict was supplied —
  modelling a reviewer who approves a benign-looking "remove unused rule"
  cleanup PR).
- **push 2** — ship the malicious prod change with NO verdict, based on the
  already-weakened tree (`base` = push-1 head). Result:
  `push2_blocked=False` — **the malicious prod code ships with a GREEN gate,
  zero verdict, and no flag.**
- **control** — the SAME two edits in ONE push off the strong base:
  `single_push_blocked=True` (A3 holds).

Raw:

```
push1_policy_weaken:  blocked=False, reasons=[]
push2_malicious_prod: blocked=False, reasons=[]      <-- unreviewed prod code shipped
control_single_push:  blocked=True   (A3 baseline-union fires)
```

**Why it is a genuine gap despite the dependency.** A3's baseline is only ever
`args.base` — the *immediately-preceding* merge. Once a weakening has landed in
push 1, push 2's baseline is already weak and the malicious code faces no rule.
The escalation over plain key-custody: the reviewer of push 1 sees only a rule
removal with **no attached payload**, and push 2 has **no reviewer at all** —
so the bad code is shipped without any single human ever approving *that code*.
The gate's own stated A3 invariant ("a single push cannot both weaken the
policy and rely on the weakened policy to pass") is literally true per-push but
is defeated by using two PRs.

**Blast radius.** Any rule (including hard-floor rules) can be permanently
disarmed for all *future* pushes once a policy-weakening merge lands; the
subsequent exploit push needs no verdict and trips no flag.

**Honest caveat.** This is **not** key-free: push 1 requires a real Reid/Cyra
verdict (key custody / a complicit or inattentive reviewer). It is the
disclosed "a merged weakening lowers the floor" boundary, sharpened into a
confused-deputy erosion.

**Minimal standalone repro:** run
`python3 gate-arena/bypass/run_bypass_corpus.py` and read the `A14` entry in
`results/bypass-scorecard.json` (`evidence.push2_malicious_prod.blocked` is
`false`; `evidence.control_single_push.blocked` is `true`). The mechanic is
purely `tessctl gate ci --base <push1-head> --head <push2-head>` returning
green after a prior weakening merge.

**Proposed fix design (NOT implemented — architecture decision).** Anchor A3's
baseline to a longer-lived *protected* policy reference rather than only the
immediately-preceding merge — e.g. a committed, signed policy-baseline anchor
(`.tess/gate/policy-baseline.<sig>`) that the gate diffs the *current* policy
against on every push, so any net weakening relative to the anchor (not just
relative to the previous commit) requires an explicit, signed re-baselining
sign-off. This makes a weakening durable-visible across pushes instead of
silently becoming the new normal after one merge.

## A15 — dependency / supply-chain injection (ungoverned manifest)

**Verdict: BYPASS FOUND (open) — key-free.**

**What is exploitable.** The shipped self-protection rule
(`tess-os-security-tier-doctrine`) deliberately governs `.github/workflows/**`
(MEDIUM-1: guard the gate's own CI trigger so a PR can't keep the required
check name while neutering its step). But the **dependency manifests those
governed workflows install-and-execute** are in **no** policy glob. This repo's
real, committed `.github/workflows/ci.yml` runs:

```yaml
      - name: Install dev dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements-dev.txt      # <-- ungoverned input
      - name: Run test suite (pytest)
        run: python -m pytest                        # <-- imports/executes it
```

and, for the Node side, `npm ci` from `create-tess/package-lock.json`
(ci.yml lines 74–75) — npm lifecycle scripts (`postinstall`) execute arbitrary
code. None of `requirements-dev.txt`, `pyproject.toml`, `package-lock.json`,
`create-tess/package-lock.json`, or `gui/package-lock.json` matches any rule in
the forked-verbatim shipped policy. So an unreviewed edit to a manifest injects
code that a **governed, unmodified** workflow then installs and executes — with
zero covering verdict, and the ship-gate green.

Empirical result (pristine shipped engine):

```
manifest_edit:          blocked=False, changed_paths=["requirements-dev.txt"], reasons=[]  # GREEN
control_workflow_edit:  blocked=True   # editing ci.yml directly IS gated (.github/workflows/**)
```

The control proves the asymmetry: the gate protects the trigger **file** but
not the trigger's **supply chain**. You don't need to neuter `ci.yml` (A8's
class, blocked) — you poison what `ci.yml` installs.

**Blast radius.** Arbitrary code execution in CI (pytest imports installed
packages; `npm ci` runs lifecycle scripts) under the CI job's token/secret
scope, shipped with a green ship-gate and no review — via a
typosquat/malicious pin/dependency-confusion edit to an ungoverned manifest.
This defeats the *spirit* of the MEDIUM-1 `.github/workflows/**` protection: the
workflow's dependency inputs are an unguarded extension of the exact trust
surface that rule was written to close.

**Boundary (disclosed, same posture as A8/A11).** The arena proves the
**engine** returns green for the manifest edit; the install-and-execute
(RCE-in-CI) consequence is grounded in this repo's real committed `ci.yml`, not
spun up inside the arena (which cannot run GitHub Actions).

**Minimal standalone repro** (no keys; edits only an ungoverned file):

```bash
# From a fixture repo carrying the forked shipped policy + a ci.yml that runs
# `pip install -r requirements-dev.txt` (see attack_A15 in attacks.py), at BASE2:
echo "evil-telemetry==6.6.6  # attacker-injected" >> requirements-dev.txt
git add requirements-dev.txt && git commit -qm 'pin an extra dev dependency'
HEAD=$(git rev-parse HEAD)
TESS_ROOT="$PWD" python3 .tess/bin/tessctl gate ci --base "$BASE2" --head "$HEAD" --json
# EXPECTED: "blocked": false — requirements-dev.txt matches no rule; the
# governed, unmodified ci.yml would `pip install` and pytest-execute it in CI.
```

**Proposed fix design (NOT implemented — coverage decision for Tess + Xavier).**
Add the dependency-manifest / lockfile surface to
`tess-os-security-tier-doctrine`'s globs in `core/policy/policy.yaml`, so a
supply-chain edit needs a covering, signed Reid/Cyra verdict — exactly the
mechanism MEDIUM-1 used for `.github/workflows/**`. Suggested globs (tune to the
repo's real inputs):

```yaml
        - requirements*.txt
        - pyproject.toml
        - uv.lock
        - "**/package-lock.json"
        - "**/package.json"
```

This is left as a recommendation rather than applied here because *which*
manifests to govern (and whether to also add CODEOWNERS/dependency-review on
those paths, GitHub-side) is a project-coverage decision, and this NO-MERGE
red-team PR should not unilaterally change the shipped product policy.

## Boundaries this expansion does NOT change

- **Key custody** and **repo-admin / branch-protection power** remain untested
  boundaries, exactly as `README.md` already discloses. A14 depends on the
  former; A13a's residual window and A8/A11/A15's real-world execution depend on
  the latter.
- "12/15 blocked" (or "13/15" after the A13 fix commit) is a **corpus score**,
  not a proof of unbypassability. It means precisely these 15 pre-registered
  attacks were run and these were the outcomes — nothing more.
